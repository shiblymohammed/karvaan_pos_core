# Workflow and UX review

Reviewed 15 October 2026. These changes are local and have not been deployed to the VPS. This review combines source inspection with isolated HTTP, WebSocket, database, and browser-storage tests; it does not replace restaurant acceptance testing.

## Fixed in this update

| Workflow | Verified problem | Change |
| --- | --- | --- |
| Insufficient stock | Checkout and dispatch could make stock negative without approval. | The server aggregates recipe requirements, requires manager approval for shortages, and audits the manager, cashier, reason, quantities, and sale reference. The signed approval is limited to that operation, quantities, and shortage; increased shortages or revoked managers require fresh approval. Retries keep the original identity. |
| Approval review | Staff lacked a way to approve a queued shortage or review exceptions. | Approval is available at checkout/dispatch and from the pending-actions panel. Managers can review the latest 100 exceptions in Inventory & Recipes, Waste tab. PINs are not saved in queued sale payloads. |
| Waste | A loss record and its stock movement were independent writes, and quantities could be silently clamped. Server logs were not restored consistently. | One idempotent server transaction records the waste, historical cost, operator, and stock deduction. Invalid quantities preserve the form. Server snapshots restore logs. Older records without known costs are labelled accordingly; the view covers the latest 500 logs. |
| Recipe costing | Waste allowance and preparation details disappeared on reload, and displayed ingredient cost differed from actual consumption. | Waste percentage, instructions, and batch size persist. Consumption and saved invoice recipes include the same allowance. Future cooked-return losses use saved ingredient costs without deducting stock twice. |
| Park and resume | Customer phone, discount, and invoice identity were lost. The cart cleared before saving succeeded. An event object could be passed as a park label. | Park/resume retain billing metadata and preserve the cart after failure. Temporary operations block conflicting clicks. Pending drafts survive reconnect snapshots, and board revisions reject stale snapshots after another terminal resumes an order. |
| Kitchen | Served was sent twice, client-side readiness also changed delivery separately, and failed sends could still clear the cart or open a successful print view. | Status updates await confirmation, dependent client delivery writes are removed, and failed sends preserve unsent food. KDS and printed tickets use the same order number. Pending tickets identify their unconfirmed state. |
| Delivery | Sync sent a rejected legacy snapshot but reported success. Missing kitchen tickets implied food was packed. Paid cash was labelled paid online; completed rows disappeared automatically. | Refresh reads current server data. Readiness follows server status. Paid methods and pending changes are explicit. Payment confirmation waits for the server, and completed deliveries stay until explicitly archived. |
| Customer repayment | The customer screen announced success before the server recorded money and defaulted silently to cash. | Both customer and ledger screens use the same amount/payment-method form and show success only after confirmation. |
| Staff management | Existing staff could not be edited without resetting passwords. A contact field was never persisted. Deactivation had no confirmation. | Password/PIN replacement is optional for existing accounts. The persisted phone field is used. Saves preserve inputs on failure; a corrected rejected edit retries its original action. Deactivation requires confirmation, and own-role/access changes are blocked. Staff caches omit plaintext credentials. |
| HTTP tablet clients | Some actions depended on randomUUID being available. | A cryptographically random UUID fallback supports those clients for parking, inventory, delivery, and refunds. |
| Desktop workflow | Development started the new frontend without rebuilding the bundled backend, and packaging relied on an already-generated database client. | Desktop development/build commands regenerate Prisma and compile the backend before starting or packaging the frontend. The commands and JSON configuration are checked; a native installer has not been built in this review. |
| Fresh caches | Menu, inventory, and waste screens could display sample business data. | Fresh stores start empty and load server data. New ingredient forms start with zero stock/cost instead of invented opening balances. |
| Dates | Today could select yesterday before 05:30 IST because report filters used UTC dates. | Dashboard and history filters use the same Indian business day as the backend. Calendar date parsing avoids timezone-induced day shifts. |
| Misleading features | QR waiter calls only displayed an alert, and the prep recommendation was always 35 portions while claiming to use sales history. | QR is explicitly a menu preview with no live customer-order claims. Prep planning is labelled as a manual recipe calculator and does not claim to reserve stock or forecast sales. |

## Remaining work, in priority order

| Priority | Gap | Required resolution |
| --- | --- | --- |
| P1 | Combo Studio is not a complete server workflow. Its component metadata is absent from the backend product schema, and its changes do not invoke the menu manager's save path. | Add an acknowledged combo command, persistent composition, component ownership/deletion checks, and an explicit recipe policy. Test reload, two-device editing, sales, returns, and ingredient consumption. Until then, do not rely on device-only combo contents for stock accounting. A normal menu item with its own complete recipe is the supported accounting path. |
| P1 | Independent local and VPS databases are not a safe financial multi-master system. | Use one operational backend for active terminals. Bidirectional operational writes require a separate replication/conflict design. |
| P1 | Local installers still have demo provisioning paths, and existing installations may retain demo credentials or older ambiguous data. | Build clean installers with private first-run credentials; review existing accounts and reconcile older device records. Do not guess original cashiers or historical quantities. |
| P2 | Public customer QR ordering and waiter requests do not have table/customer sessions or acknowledged notifications. | Design signed table sessions, protected guest actions, order review, duplicate prevention, and staff acceptance before public rollout. The staff preview remains read-only. |
| P2 | Automatic demand forecasting is not implemented. | Use real sales history and validate forecasts against actual prep/waste outcomes before labelling recommendations as predictions. |
| P2 | Packaging rules vary by order type and recipe versions can change while kitchen orders are open. | Define explicit packaging/recipe-version rules and reservation or consumption timing. Current accounting consumes saved sale/dispatch recipes; packaging must be configured deliberately. Avoid changing production recipes midway through preparation until version/reservation support is designed. |
| P2 | Frontend tooling has 10 dependency findings: 7 high and 3 moderate in the current audit. | Coordinate Vite, Tailwind, and PWA tooling upgrades and verify browser, desktop, and Android builds. Do not apply a forced major upgrade directly to production. Production-dependency audits are distinct from this full tooling audit. |
| P2 | Large frontend bundles, unrestricted annual history loading, and physical hardware/restore acceptance remain. | Add server pagination/aggregation and measured bundle improvements; exercise real printers, offline devices, and an isolated restore. These have not been verified on restaurant hardware. |

## Release checks

Back up first. Deploy backend and frontend together, refresh browser/PWA clients, and rebuild installed clients. Keep database/media volumes. The additive database fields must be applied by the normal startup upgrade; do not approve destructive schema changes automatically.

Check `/health` for `inventoryWaste: 1` and `stockShortageApproval: 1` as well as the earlier menu/admin capabilities. Configure an active manager's PIN before testing shortages. Test a normal sale, a short sale approved by a manager, a worsened shortage, a queued approval retry, a failed KOT, park/resume with credit-customer details, and one waste entry retried after a lost acknowledgment. Check invoice count, stock movements, approval history, and customer balances.

The current automated suites have 110 POS tests and 12 local print-worker tests. See [PRINTING_WORKFLOW.md](PRINTING_WORKFLOW.md) for the subsequent printing changes and rollout requirements. Backend compilation and frontend type checking/production PWA build passed. The separate production-only dependency audit could not be refreshed because the npm registry DNS lookup failed; no fresh production-only result is claimed. Live VPS transactions, Docker runtime on this workstation, distributed installers, real tablet/desktop behavior, physical printers, and actual bank/UPI transfers have not been exercised by this review.

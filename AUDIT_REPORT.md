# Deployment and workflow audit

Audited on 14 October 2026. This review covers the repository, installed dependency tree, production dependency advisories, local builds, and isolated HTTP/WebSocket tests. The live VPS, real printers, Android installation, Windows installer, and concurrent restaurant terminals were not exercised.

## Changes completed locally

| Area | Confirmed problem | Change |
| --- | --- | --- |
| Authentication dependencies | `@nestjs/passport@12` requires NestJS 11/12 while this backend runs NestJS 10. A clean install rejects the combination. | Pinned Passport integration to the verified compatible 10.0.3 release. |
| Reproducible builds | Containers used `npm install`; the backend hid peer conflicts with `--legacy-peer-deps`. | Both containers now use Node 22 and `npm ci`. Lockfile download URLs and project registries use official npm. Capacitor 8 requires Node 22. |
| Dependency patches | Production audits initially reported critical advisories in backend `proxy-addr` and Android Capacitor, plus other patchable findings. | Applied updates within the existing declared version ranges, without forced major upgrades. |
| Cloud initialization | The cloud seed created owner, manager, and cashier demo accounts with public default passwords and logged the administrator password. Seed failures were ignored. | New cloud databases create only a hashed private super administrator. Default cloud passwords are rejected, secret logging is removed, and seed failure stops startup. Creating owners/admins requires an explicit password of at least eight characters. Existing accounts are not modified. |
| Database updates | Every container startup passed `--accept-data-loss` to Prisma. | Removed automatic consent to destructive schema changes. A destructive change now stops startup for explicit migration planning. |
| Backups | The cloud script called a missing `sqlite3` executable, hid its failure, then archived the changing live database and WAL files. | Added SQLite to the runtime image. The script creates a consistent snapshot, checks database/archive integrity, copies uploads, and only then publishes the archive. A failed snapshot cannot be reported as success. |
| Deployment status | The deploy script reported success even after the backend health timeout. | Timeout now prints backend logs and exits unsuccessfully. |
| Counter checkout → kitchen | Checkout committed the sale and broadcast the kitchen ticket, then the frontend queued another `fire_order`. The backend rejected it as already settled, blocking subsequent queued actions. | Removed the second kitchen submission; checkout's backend notification supplies the ticket. |
| Delivery payments → credit ledger | Paid/prepaid deliveries were added as positive `UNPAID` customer debts. | Removed these incorrect ledger writes and the initial sample debt for new browser storage. Existing saved entries are not rewritten. |
| Cloud media | Promo uploads constructed an HTTP URL on port 3001 even on HTTPS or separate-backend deployments. | Promo URLs use the configured backend resolver. Category/item upload and image-loading fixes from the previous task are retained. |
| QR screen | Kitchen submissions omitted product IDs, so backend catalogue validation rejected them. | Submissions now include product IDs. This does not implement anonymous customer ordering. |
| First cloud visit | The app inferred a same-origin backend but still treated the server as unconfigured, reopening setup after reload. | The setup check now recognizes the same inferred backend. |
| Printer acknowledgment | The API client returns `{ success }`, while the receipt checked `res.data.success`; even a successful network print fell through to another print dialog. | Corrected the success check. Hardware selection remains incomplete. |
| Verification pipeline | No repository workflow checked fresh dependency installs, builds, tests, shell syntax, or container builds. | Added `.github/workflows/verify.yml` with these checks. Shell files explicitly retain LF line endings. The workflow does not deploy. |

## Validation and limits

- Backend TypeScript build passes.
- Frontend type check and Vite/PWA production build pass. Build output was written to a temporary directory to preserve the pre-existing change in `frontend/dist/index.html`.
- All 29 regression tests pass. Added coverage includes direct counter checkout → kitchen status, cloud seed isolation/idempotency, required initial account passwords, and same-origin setup detection. Existing tests cover upload retrieval, authentication, tenant isolation, checkout retries, stock side effects, and SQLite backup consistency.
- Both updated lockfiles pass `npm ci --dry-run`; authentication peer compatibility is clean, and the frontend dependency tree has no reported peer conflicts. A full clean Linux install is delegated to the added CI workflow.
- Production dependency audit: backend 9 findings (2 high, 6 moderate, 1 low), frontend 0. Development/build tooling still has advisories; remediation requires coordinated Vite/Tailwind/tooling changes. Zero reported advisories is not a security guarantee.
- Shell syntax is checked separately for each script. Actual container builds and the new backup shell workflow could not be run locally because Docker's Linux engine is not running. The new GitHub workflow has not run remotely yet.
- Live payment settlement, real printer output, concurrent/offline multi-terminal recovery, and installed native app upgrades still require staging acceptance tests.

## Rollout sequence

1. Independently back up the live VPS and verify that the copy can be read. An existing backend image does not yet contain the newly added SQLite command.
2. Review old seeded demo accounts and erroneous delivery ledger entries. Keep real sales and debts intact.
3. Transfer/commit the source and lockfile changes, then rebuild both backend and frontend containers. Confirm `.env` contains the existing private `SUPER_ADMIN_PASSWORD` and JWT secret.
4. Run the new snapshot backup script after the rebuilt backend is running. Confirm `/health`, login, menu image upload, a counter sale, and kitchen progression.
5. Resolve delivery billing, durable credit/refunds, and multi-terminal conflict handling before relying on those flows for accounting. Plan the remaining backend security upgrade in staging.
